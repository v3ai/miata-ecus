# F04 Firmware build, release, update and tuning-software experience

Tags: VERIFIED (read today in file/URL), INFERRED (reasoned), UNVERIFIED (memory/secondary). Today 2026-11-16.

## Summary
1. The CI (`repo/.github/workflows/firmware.yaml`) builds firmware + ini but only as GitHub Actions *artifacts*; there is no release step, no tag, no checksum, no signed-off checklist. A customer must go to the Actions tab, open a run and download zips (firmware/README.md "Getting the firmware"). Artifacts expire (GitHub default retention 90 days: UNVERIFIED, from memory; repo-configurable) and need a GitHub login to download (UNVERIFIED, memory).
2. `uploads: ''` in the build step (firmware.yaml) disables the upload to rusefi.com/online. So the signature `rusEFI master.<date>.miata-ecu.<hash>` has NO online ini; TunerStudio/console cannot fetch a matching ini by themselves. The customer must use the ini from the same build. Signature = white label + branch + build date + short board name + hash of config layout; one ini per exact build (rusEFI wiki "INI lookup logic").
3. The F4 target does not embed the ini on the ECU (`EFI_EMBED_INI_MSD FALSE`, efifeatures.h:406-409), so the board cannot hand the customer its own ini over USB mass storage. Embedding would not fit: the ini is ~930 kB (gzip ~196 kB, measured on rusefi_f407-discovery.ini as proxy) vs 77 kB spare in the image (VERIFICATION.md:102). INFERRED.
4. Pinned rusEFI 1374bd07 is dated 2026-10-30; rusEFI master is 239 commits ahead today (GitHub compare API, VERIFIED). Only 17 days old, but moves ~14 commits/day. fw-custom-example has a daily "update rusefi reference" workflow (wiki Custom-Firmware); this repo has none, so it is a manual bump + rebuild + re-verify task.
5. Not pre-flashed in the plan: customer must DFU-flash (BOOT+RESET on the daughterboard, inside the case) OR is assumed to receive a flashed board; INSTALL.md says "with firmware loaded" (INSTALL.md:110) and the bench-check step 3 asks the customer to press "Flash on-board wideband". Seller can do all of this on the bench in one USB session before shipping.
6. The motherboard is year-specific, so the seller knows the year at sale; the customer-side "pick your year" step (and the 2001-02 vs 2003-05 trap) can be removed.
7. TunerStudio is a paid product for full features; rusEFI's own free "rusEFI tuner" is the wiki-recommended first choice (wiki Connectivity page). The repo's INSTALL.md says only "a laptop with TunerStudio" and gives no cost/licence info.

## Maintenance cost of a fork / custom board
- Custom board is a separate repo with the rusEFI submodule (shallow, `.gitmodules`). Every bump requires: regenerate config, rebuild, rerun check_pins/check_image/sim tests, re-verify the ini buttons, re-test on a real car (no hardware today). rusEFI changes ~239 commits per 17 days; breaking config changes happen (the repo already had to fix CAN bus numbering). INFERRED.
- Pin the submodule to a release/LTS ref rather than master: the action understands branches beginning with `lts` (custom-board-build/action.yaml "Set Build Env Variables", VERIFIED). Whether rusEFI currently publishes an LTS branch: not checked.
- Official acceptance: rusEFI's new-board procedure (firmware/config/boards/readme.md) = add the board folder + gen_config.sh pair + build-firmware.yaml entry + connector yaml. Result: build on rusefi.com/build_server, ini uploaded online under rusefi.com/online/ini, console recognises it. Needs maintainers to accept a new board with unverified hardware: they list hardware like Hellen/MRE/Proteus; acceptance policy not read (UNVERIFIED). The Miata-specific year presets and the wideband UART flasher are board-local code that would have to be upstreamed or kept as hooks.
- FOME: fork of rusEFI since 2023, "most rusEFI boards compatible, will diverge" (search result, secondary). FOME publishes fixed GitHub release assets (e.g. release_260501_02 2026-06-04) with bundles for hellenNA6, hellenNA8_96, hellen-nb1 (GitHub API, VERIFIED) but those are Hellen hardware, not this board. Porting the board to FOME means a second build of the board code against a diverging tree; benefit: stable dated releases and wiki.fome.tech docs. Miata-relevant differences beyond that not verified.
